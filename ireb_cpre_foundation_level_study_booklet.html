Unit 1.1 — Definition of Requirements Engineering

What is a Requirement & Requirements Engineering?

Weight: ~7% of Exam
Plain-English Explanation
Requirements are not solutions or code. A requirement is simply a statement about what a system needs to deliver or what conditions it must satisfy so stakeholders achieve their goals. RE is the disciplined process of discovering, shaping, documenting, checking, and maintaining those needs.
Official IREB Terminology
Requirement: A condition or capability needed by a user to solve a problem or achieve an objective. A capability that must be met or possessed by a system to satisfy a contract, standard, or specification.
System Boundary: Separates the planned system from its context environment.

The Three Types of Requirements

Requirement Kind IREB Definition Everyday Analogy (Car) IT System Example (Hospital App)
Functional Requirement (FR) Defines a result, behavior, or function provided by the system. The car must accelerate from 0 to 100 km/h when pressing the pedal. The system shall send an SMS alert to on-duty doctors when cardiac telemetry exceeds 140 bpm.
Quality Requirement (QR) Pertains to non-functional quality attributes (performance, reliability, security, usability). The car cabin noise level must remain under 60 dB at highway speeds. Telemetry notifications must reach the mobile handset within 1.5 seconds under 99.9% uptime.
Constraint An organizational, technical, legal, or physical limitation that restricts the solution space. The vehicle width cannot exceed 2.1 meters to fit EU standard garage bays. The database must comply with GDPR Article 17 ("Right to erasure") and run on Linux kernels.
Resit Exam Trap
Questions often disguise constraints as functional requirements. "The system shall be written in Java Spring Boot" is NOT a functional requirement—it does not describe user behavior; it is a technical constraint restricting implementation!
Memory Hook: "F-Q-C"
Function = What it does.
Quality = How well it behaves.
Constraint = What handcuffs the engineers.
The System vs Context Boundary Framework
Irrelevant Environment
➔ [Context Boundary] ➔
System Context (Stakeholders, Laws, Legacy Systems)
➔ [System Boundary] ➔
The System To Be Built
*Exam Tip: The Context Boundary filters what matters from what can be ignored. The System Boundary demarcates what is inside our project scope.
Unit 2 — Fundamental Principles

The 9 Foundational Principles of IREB

Weight: ~15% of Exam

The IREB Foundation syllabus centers on 9 universal principles that apply equally in traditional waterfall, hybrid, and agile contexts. Memorise these verbatim:

# Principle Name Core Essence Exam Trap to Watch Out For
1 Value Orientation Requirements are a means to an end, not an end in themselves. An RE activity is only justified if it adds project value and reduces risk. Writing a 200-page spec for a simple mobile widget violates value orientation. RE effort must match risk.
2 Stakeholders RE is about satisfying the desires and needs of stakeholders. Direct and indirect stakeholders must both be considered. Ignoring indirect stakeholders (e.g., system maintainers or compliance regulators) often fails certification.
3 Shared Understanding Explicit specs are only needed where true shared understanding is absent. Shared understanding is built through collaboration and feedback. Assuming that "because we wrote it down, everyone understands it" is the classic false assumption.
4 Context Systems cannot be understood in isolation; context shapes every requirement. Forgetting interfaces with external legacy systems or hardware tolerances.
5 Problem, Requirement, Solution Distinguish sharply between the problem in context, the requirement needed, and the specific technical solution. Accepting stakeholder requests that state architectural solutions (e.g., "Build an Oracle DB") without uncovering the problem.
6 Validation Non-validated requirements are useless. Validate early, continuously, and repeatedly. Believing requirements are valid just because the client signed off without walking through examples.
7 Evolution Requirements change is normal, not an accident. Changing business environments demand adaptive engineering. Treating changes as disruptions instead of managing them systematically via change control.
8 Innovation Stakeholders often don't know what is technically possible. Requirements engineers must spark innovation, not just take orders. Thinking RE is merely passive "note-taking". The engineer is a proactive co-creator.
9 Systematic Work Apply methods, notations, and processes deliberately, tailoring them to project risk. Using ad-hoc methods under time pressure, which leads to defects in production.
Acronym to Memorise the 9 Principles
V-S-S-C-P-V-E-I-S: "Value-driven Stakeholders Share Context; Problems Validated Evolve Into Systems."
Unit 3 — Work Products & Documentation

Documentation Forms, Templates & UML Modeling

Weight: ~22% of Exam
Natural Language & Sentence Templates
Natural language is universally understood but prone to ambiguity. IREB heavily tests Rupp's Sentence Template for standardizing requirements statements.
Rupp's Template Structure
<Stakeholder / System> + <Obligation: SHALL / SHOULD / WILL> + <Action / Capability> + <Object / Condition>

Modal Verbs and Their Legal Degrees

Modal Verb Degree of Obligation Exam Meaning
SHALL (MUSS) Legally binding / Mandatory Must be implemented; failure to do so is a contract breach.
SHOULD (SOLLTE) High recommendation / Desirable Should be implemented unless strong trade-offs or cost overruns justify omission.
WILL / CAN (WIRD / KANN) Future intent / Optional Nice to have; reserved for future scope or secondary releases.
Four Ambiguity Traps in Natural Language
  1. Nominalisation: Transforming processes into nouns (e.g., "The user registration will occur" hides WHO registers WHOM and WHEN).
  2. Incomplete Condition: "If timeout occurs, notify user" (What happens if timeout does not occur?).
  3. Universal Quantifiers: Words like "all", "never", "always", "every" usually hide unspoken edge cases.
  4. Vague Adjectives: "Fast", "user-friendly", "robust", "secure" are unverifiable unless tied to measurable metrics.

The Three UML Model Perspectives Tested in IREB

Structure Perspective
UML Class Diagram
Objects, classes, associations, multiplicity (1..*, 0..1), attributes.
Functional Perspective
Use Case Diagram
Actors, Use Cases, <<include>> (mandatory reuse), <<extend>> (optional branch).
Behavioral Perspective
Activity & State Machine
Control flow, forks/joins, swimlanes, states, transitions triggered by events.
Unit 4 — Requirements Elaboration

Sources, Elicitation Techniques, Kano & Conflict Resolution

Weight: ~25% of Exam
The 3 Requirements Sources
1. Stakeholders: Humans with opinions, roles, and stakes.
2. Documents: Standards, user manuals, laws, competitor audits.
3. Systems in Operation: Legacy databases, competitor tools, sensors.
The 5 Elicitation Technique Classes
1. Survey: Interviews, Questionnaires.
2. Creativity: Brainstorming, Mind Mapping, 6-3-5.
3. Document-centric: System Archaeology, Re-use.
4. Observation: Field observation, Apprenticing.
5. Support: Prototyping, Scenarios, Role Play.

The Kano Model in IREB Examinations

1. Basic Factors (Dissatisfiers): Taken for granted. If absent, extreme dissatisfaction. If present, customer is merely neutral (e.g., brakes in a car, login button working).

2. Performance Factors (Satisfiers): Linearly proportional. More performance = more customer happiness (e.g., battery life, processing speed).

3. Excitement Factors (Delighters): Unexpected features. If absent, zero disappointment because they weren't anticipated. If present, delight (e.g., auto-detecting flight delays and rescheduling car rental).

*Exam Trap: Over time, Excitement factors degrade into Performance factors, and eventually become Basic factors!

Conflict Resolution Techniques

Technique How It Works Best Used When
Agreement (Consensus) Parties discuss and negotiate until all stakeholders genuinely align. High-stakes architecture decisions with collaborative teams.
Compromise Each party concedes some demands to meet in the middle. Tight deadlines where win-win cannot be achieved immediately.
Voting Majority vote decides the chosen requirement path. Equal peer groups with non-critical stylistic differences.
Definition Variant System is designed to accommodate both variants (e.g., configurable settings). Different user personas require conflicting workflows.
Overruling (Authority) A senior executive or Product Owner commands the final decision. Deadlocks or legal/regulatory non-negotiables.
Unit 5 — Process & Working Structure

Configuring the RE Process: Linear vs Iterative

Weight: ~10% of Exam
The Three Process Facets
IREB defines 3 fundamental spectrums for configuring an RE process:
1. Linear vs Iterative: Waterfall sequence vs Agile sprint cycles.
2. Prescriptive vs Explorative: Strict contractual plans vs hypothesis prototyping.
3. Customer-Specific vs Market-Oriented: Bespoke single client vs off-the-shelf software.
Resit Exam Trap
There is no single "correct" RE process in IREB. The syllabus mandates that RE must be tailored to the risk, domain volatility, stakeholder availability, and regulatory landscape.
Unit 6 — Requirements Management

Life Cycles, Attributes, Views, Baselines & Traceability

Weight: ~15% of Exam
Traceability Dimensions
Pre-RS Traceability: Traces a requirement back to its origin (stakeholder statement, law, meeting memo).
Post-RS Traceability: Traces forward to implementation code, architecture modules, and test cases.
Horizontal: Across different work products.
Vertical: Across different levels of abstraction.
Baselines & Configurations
Baseline: A stable, formally approved version of a set of work products that serves as a basis for further development and can only be changed via formal Change Control.
Configuration: A consistent set of uniquely identified work product versions.

Unit 7 — Tool Support

Tool Classes, Introduction Pitfalls & Best Practices

Weight: ~6% of Exam
The Golden Rule of Tooling
"A fool with a tool is still a fool."
Automating an unstructured, chaotic process only creates automated chaos. You must establish clear roles, workflows, and notation standards before deploying specialized software tools.
4 Core Tool Categories
1. Requirements Management Tools: Jira, DOORS, Polarion (Attributes, traceability, baseline control).
2. Modeling Tools: Enterprise Architect, Camunda (UML, SysML, BPMN).
3. Collaboration Tools: Confluence, Miro, Teams (Discussions, distributed elicitation).
4. Testing / Traceability Tools: TestRail, Zephyr (Linking specs to test suites).
